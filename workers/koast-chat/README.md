# Website chat Worker

Recovered from the deployed `koast-chat` Worker on 2026-10-16 (active version 45eea2db, secret-only successor 79e6ba32), then migrated to OpenAI Responses. This folder is the source of truth. Cloudflare Workers Builds deploys it from main using the existing GitHub connection and Workers Builds token. Root directory: workers/koast-chat; build: npm run check && npm test; deploy: npx --yes wrangler@4.151.1 deploy; preview builds disabled. GitHub Actions provides validation only; the main Pages job excludes the entire workers folder. The Pages deployment token does not have access to this Worker and must not be reused for its deployment.

Runtime secret: `OPENAI_API_KEY`, installed in Cloudflare, never in Git or Pages. Optional runtime variable: `OPENAI_CHAT_MODEL` (default `gpt-6.1-sol`). The production key must be present before deployment. Old Anthropic secrets can remain unused during rollback validation.

The website remains a tool-less information assistant: same live llms.txt fact source, conversation limits, booking/refund handoff rules, reply JSON, allowed website origins, and human fallback. `photo-input.mjs` owns transient image validation, re-encoding, metadata removal and the image-content projection. Responses are not stored by OpenAI (`store:false`).

Support and planning instructions answer the current question first. The site's `generate.py` / `enhance` owns public support guidance in `llms.txt`, including existing rides, pickup help, accepted ride terms, receipts/billing, lost property and complaints. General support questions get guidance without starting a trip-planning interview; private booking/refund cases route to the existing portal or team. Kopilot cannot look up accounts, issue refunds, create tickets, contact staff or transfer conversations. Planning uses retained context, asks at most one needed follow-up, and avoids repeat questions and unnecessary personal information before directing to the quote portal or team. Output remains plain text with full fact-sourced URLs; the website independently renders only its fixed destination allowlist as native links. Prompt tests use a stubbed model transport and verify supplied instructions/context, not live model adherence.

Validate with `npm run check`, `npm test`, and an esbuild ESM bundle check. Run a synthetic chat through the live website after a deployment; API-key validation alone does not verify this integration.


## Protected photo input (local candidate, not activated)

The public assistant can receive up to two photos across the retained request history. Only strict JPEG data URLs reach this Worker; the browser accepts JPEG/PNG/WebP originals up to8MiB and re-encodes them before sending. The server independently bounds the JSON stream to1.1MiB, each decoded JPEG to350KiB, longest edge1280px and decoded pixels1,638,400 before the image decoder. It validates canonical Base64 and JPEG segment/scan structure and rejects trailing payloads. Original filenames and URLs are never accepted.

Cloudflare `IMAGES.info` verifies dimensions; `IMAGES.input(...).transform(...).output(...)` must decode and re-encode the photo. The server validates that result and independently strips every JPEG APP/COM metadata segment, including between progressive scans, before creating an OpenAI Responses `input_image` part. A photo is transient request content: no R2, Files API, public image URL, filesystem write, conversation database or image logging. Existing `store:false` is retained; this flag is not a claim that the provider has no abuse-monitoring retention. Image text is untrusted input and cannot authorize account/booking/payment actions. No biometric identification or sensitive-trait inference.

Wrangler declares `IMAGES` plus `PHOTO_RATE_LIMITER` (4 requests/minute per SHA-256 edge-IP key) and `PHOTO_GLOBAL_LIMITER` (30 photo requests/minute per shared key). Cloudflare rate limits are approximate, separately counted per location; the second binding is a location-wide guard, not a strict worldwide spending cap. Binding errors/missing key or missing trusted edge IP fail photos closed. Native rate-limit counters may retain the hashed key per provider policy; no raw IP is sent to the model or added to application logs. Ordinary text remains available without photo bindings. Origin checks are a browser boundary, not authentication; do not describe them or approximate rate limits as complete bot protection.

`GET /capabilities` returns `{photos,maxPhotos:2,maxFileBytes:8388608}` with no-store/CORS headers and no credentials. Readiness requires the current key and all three bindings; actual account plan/Images entitlement, chosen unique limiter namespaces and production transformation availability must be verified before publication. This candidate declares the binding but does not provision paid features, change secrets or activate remote image processing. Deployment remains the existing Git main/Workers Build path coordinated with the website. A fresh Worker deployment must be verified before the frontend is described as live; unavailable capabilities hide attachment entry.

Errors return a stable `error` and safe `reply`, with400/413/415/429/503 and `Retry-After:60` for rate limits. No-store applies to successful replies, errors and capabilities. Replies and thumbnails must remain text/known data URLs in the frontend, never model-supplied HTML or remote content.
